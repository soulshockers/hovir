# Spec Delta

## Purpose

Дає власнику інстансу й доповідачу швидкий спосіб перевірити, чи інстанс готовий до роботи: конфігурація, БД, Supabase API, міграції. Окремо розпізнається призупинений безкоштовний проєкт Supabase з інструкцією, як його відновити (безкоштовний проєкт Supabase призупиняється після 7 днів неактивності).

## ADDED Requirements

### Requirement: Перевірки стану інстансу
Інстанс SHALL виконувати чотири перевірки: конфігурація (`config`), підключення до Postgres (`database`), доступність Supabase API (`supabaseApi`), стан схеми (`schema`). Кожна має результат `ok`, `error` або `skipped`, а для `error` ще й машинний код причини. Якщо `config` дає `error`, перевірки, яким потрібна конфігурація, MUST отримати `skipped`.

#### Scenario: Усе справно
- **WHEN** конфігурація валідна, БД і Supabase API доступні, міграції застосовано
- **THEN** усі чотири перевірки мають результат `ok`, а загальний стан — `ok`

#### Scenario: Невалідна конфігурація
- **WHEN** обов'язкову змінну не задано
- **THEN** `config` має `error` з кодом `config_invalid`, а `database`, `supabaseApi` і `schema` мають `skipped`

#### Scenario: БД доступна, але не ініціалізована
- **WHEN** підключення до Postgres успішне, але службового запису інстансу немає
- **THEN** `database` має `ok`, а `schema` має `error` з кодом `schema_not_initialized`

### Requirement: Розпізнавання недоступного (призупиненого) Supabase
Якщо Postgres або Supabase API не відповідають чи відмовляють у підключенні, відповідна перевірка SHALL мати `error` з кодом `unreachable`. Сторінка стану MUST показувати пояснення, що безкоштовний проєкт Supabase, ймовірно, призупинено через неактивність, і покрокову інструкцію відновлення в дашборді Supabase.

#### Scenario: Supabase-проєкт призупинено
- **WHEN** Supabase-проєкт призупинено і підключення до Postgres завершується тайм-аутом або відмовою
- **THEN** `database` має `error` з кодом `unreachable`, а сторінка стану показує інструкцію «відновіть проєкт у дашборді Supabase» і пораду перевірити інстанс за день до виступу

### Requirement: Обмежений час перевірки
Кожна мережева перевірка SHALL мати власний тайм-аут не більше 5 секунд. Перевірки MUST виконуватися паралельно, а повна відповідь сторінки стану MUST формуватися не пізніше ніж за 8 секунд навіть при повністю недоступному Supabase.

#### Scenario: Supabase не відповідає
- **WHEN** хост Supabase приймає з'єднання, але не відповідає
- **THEN** сторінка стану повертає результат з кодом `unreachable` не пізніше ніж за 8 секунд від запиту

### Requirement: Сторінка стану для людей
Інстанс SHALL мати публічну сторінку `/health`. Вона показує загальний стан і результат кожної перевірки зрозумілою мовою, а для кожної помилки дає рекомендовану дію. Результат MUST обчислюватися на кожен запит і не кешуватися.

#### Scenario: Відкриття сторінки
- **WHEN** користувач відкриває `/health`
- **THEN** сторінка показує загальний стан і чотири перевірки зі статусами, актуальними на момент запиту

#### Scenario: Відсутність кешу
- **WHEN** стан інстансу змінився між двома відкриттями `/health` (наприклад, проєкт Supabase відновили)
- **THEN** друге відкриття показує новий стан

### Requirement: Машинний ендпоінт стану
Інстанс SHALL мати публічний `GET /api/health`, який повертає JSON із загальним станом, результатами перевірок, кодами причин і часом перевірки. HTTP-статус MUST бути 200, якщо загальний стан `ok`, і 503 в іншому разі. Відповідь MUST мати заголовок, що забороняє кешування.

#### Scenario: Справний інстанс
- **WHEN** моніторинг викликає `GET /api/health` на справному інстансі
- **THEN** відповідь має статус 200 і JSON із загальним станом `ok`

#### Scenario: Несправний інстанс
- **WHEN** `GET /api/health` викликано, коли БД недоступна
- **THEN** відповідь має статус 503, а JSON містить `database` з кодом `unreachable`

### Requirement: Без розкриття чутливих даних
Сторінка стану і ендпоінт стану MUST NOT розкривати значення env-змінних, рядки підключення, хости БД, тексти помилок драйверів чи стек-трейси. Дозволено показувати лише назви змінних, статуси й коди причин. Деталі помилок SHALL потрапляти лише в серверний лог.

#### Scenario: Помилка підключення з деталями
- **WHEN** драйвер БД повертає помилку з адресою хоста та ім'ям користувача
- **THEN** відповідь `/health` і `/api/health` містить лише код причини, а деталі є тільки в серверному лозі

### Requirement: Попередження на головній сторінці
Якщо загальний стан не `ok`, головна сторінка SHALL показувати помітне попередження з коротким описом проблеми й посиланням на `/health`. Збій перевірки MUST NOT ламати рендер головної сторінки.

#### Scenario: Призупинений Supabase на головній
- **WHEN** користувач відкриває головну сторінку, а БД недоступна
- **THEN** сторінка рендериться і показує попередження з посиланням на `/health`

#### Scenario: Справний інстанс на головній
- **WHEN** користувач відкриває головну сторінку справного інстансу
- **THEN** попередження не показується
