# Spec Delta

## Purpose

Синхронізація live-сесії без постійних WebSocket-серверів: дії йдуть через HTTP API, стан транслюється з сервера в канал Supabase Realtime лише на читання, а знімок стану відновлює клієнтів після перепідключення.

## ADDED Requirements

### Requirement: Дії через HTTP API
Усі дії слухачів і доповідача SHALL надсилатися HTTP-запитом `POST /api/sessions/:id/actions`. Route MUST перевіряти токен (participant або present), валідувати дію zod-схемою плагіна (`validateAction`) і відхиляти невалідні дії.

#### Scenario: Дія без валідного токена
- **WHEN** запит дії надходить без токена або з токеном іншої сесії
- **THEN** API відхиляє дію, і стан не змінюється

### Requirement: Транзакційна обробка дії
Route SHALL у транзакції читати стан слайда (`SELECT … FOR UPDATE`), викликати `plugin.server.handleAction` і зберігати новий стан. Паралельні дії по одному слайду MUST серіалізуватися без втрати змін.

#### Scenario: Одночасні голоси
- **WHEN** 50 слухачів голосують одночасно
- **THEN** у збереженому стані враховано всі 50 голосів

### Requirement: Відповідь актору в HTTP
Відповідь актору (наприклад, результат спроби «Биків») SHALL повертатися **прямо в HTTP-відповіді**. Персональні дані MUST NOT транслюватися через broadcast.

#### Scenario: Результат спроби
- **WHEN** гравець надсилає спробу в «Биках»
- **THEN** результат спроби приходить у відповіді на його запит, а не через канал

### Requirement: Трансляція стану в канал сесії
Після зміни стану сервер SHALL публікувати `PublicState`/події в канал `session:<id>` через Supabase Realtime Broadcast (server-side, з throttling ядра плагінів). Трансляції MUST бути агрегованими (без персональних даних і секретів).

#### Scenario: Оновлення після дії
- **WHEN** слухач голосує
- **THEN** сервер публікує оновлений `PublicState` у канал `session:<id>`, і екрани підписаних клієнтів оновлюються

### Requirement: Канал лише на читання для клієнтів
Усі клієнти SHALL бути підписані на канал лише на **читання**. Публікувати в канал MUST лише серверні функції: канали приватні, а RLS на `realtime.messages` забороняє клієнтам запис.

#### Scenario: Спроба публікації клієнтом
- **WHEN** клієнт з anon-ключем намагається надіслати broadcast у `session:<id>`
- **THEN** повідомлення відхиляється і не доходить до інших клієнтів

### Requirement: Знімок стану
`GET /api/sessions/:id/state` SHALL повертати публічний стан сесії й поточного слайда плюс персональний `PlayerView` для власника participant token. Знімок MUST використовуватися для першого завантаження й після перепідключення та викликати лінивий `tick`.

#### Scenario: Перше завантаження
- **WHEN** клієнт слухача відкриває сесію
- **THEN** він отримує знімок стану з поточним слайдом і своїм `PlayerView`

### Requirement: Перепідключення з експоненційною затримкою
При втраті realtime-з'єднання клієнт SHALL перепідключатися з експоненційною затримкою. Після перепідключення він MUST запитати **знімок стану**, бо пропущені broadcast-повідомлення не гарантовано доставляються повторно.

#### Scenario: Втрата мережі
- **WHEN** телефон слухача на 20 с втратив мережу, а доповідач за цей час перемкнув слайд
- **THEN** після відновлення з'єднання клієнт запитує знімок стану і показує актуальний слайд

### Requirement: Presence учасників
Присутність (online/offline) учасників SHALL показуватися через Supabase Presence (лічильник online-учасників у лобі). Офлайн-учасник MUST NOT видалятися із сесії.

#### Scenario: Учасник офлайн
- **WHEN** слухач закрив вкладку
- **THEN** лічильник online зменшується, але учасник лишається в сесії зі своїми очками

### Requirement: Затримка оновлень
Оновлення scoreboard на екрані доповідача SHALL відбуватися ≤ 1 с після дії; відповідь на спробу/голос MUST повертатися ≤ 500 мс (p95, у межах регіону).

#### Scenario: Вимірювання затримки
- **WHEN** навантажувальний тест надсилає дії від 100 слухачів
- **THEN** p95 відповіді на дію ≤ 500 мс, а екран доповідача оновлюється ≤ 1 с

### Requirement: Надійність стану
Перезавантаження будь-якого клієнта SHALL NOT втрачати стану; сесія MUST переживати перезапуск серверних функцій, бо весь стан зберігається в БД.

#### Scenario: Холодний старт функції
- **WHEN** серверна функція перезапустилася посеред сесії
- **THEN** наступна дія обробляється з тим самим станом сесії з БД

### Requirement: Закритий прямий доступ до таблиць сесій
Таблиці `sessions`, `participants`, `slide_states` SHALL мати RLS і бути закритими для `anon`/`authenticated`. Усі операції MUST іти через API routes із service role; анонімний доступ дозволено лише до каналів Realtime на читання.

#### Scenario: Запит з anon-ключем
- **WHEN** клієнт з anon-ключем читає `slide_states` через Supabase API
- **THEN** даних не повернуто
