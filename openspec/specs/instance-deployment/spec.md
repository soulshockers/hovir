# instance-deployment Specification

## Purpose

Дає змогу будь-кому розгорнути власний інстанс платформи на безкоштовних тарифах Vercel + Supabase в один клік і без ручних кроків з базою даних (перший пункт P0 дорожньої карти MVP).

## Requirements

### Requirement: Розгортання кнопкою Deploy to Vercel
README репозиторію SHALL містити кнопку «Deploy to Vercel». Вона клонує репозиторій у новий Vercel-проєкт і під час створення пропонує підключити Supabase через Vercel Marketplace, щоб обов'язкові змінні підключення підставилися автоматично.

#### Scenario: Деплой з README
- **WHEN** користувач натискає «Deploy to Vercel» у README і проходить майстер Vercel з підключенням Supabase
- **THEN** Vercel створює проєкт з обов'язковими змінними підключення до Supabase, і першому деплою не потрібно вручну вводити жодну обов'язкову змінну

#### Scenario: Опційні змінні задокументовано
- **WHEN** користувач читає README
- **THEN** README перелічує опційні змінні `INSTANCE_PASSWORD`, `DEFAULT_LOCALE`, `RESULTS_RETENTION_DAYS` з дефолтами й описом, де їх задати у Vercel

### Requirement: Автоматичне застосування міграцій під час деплою
Кожен production- і preview-деплой на Vercel SHALL застосувати всі ще не застосовані міграції БД до того, як нова версія почне обслуговувати запити. Власник інстансу MUST NOT виконувати жодних ручних SQL-кроків: Postgres-схема, RLS-політики й інші об'єкти БД застосовуються автоматично.

#### Scenario: Перший деплой на порожню БД
- **WHEN** відбувається перший деплой інстансу з підключеним порожнім Supabase-проєктом
- **THEN** усі міграції застосовуються, і після завершення деплою сторінка стану показує «міграції актуальні»

#### Scenario: Повторний деплой без нових міграцій
- **WHEN** деплой відбувається, а всі міграції вже застосовано
- **THEN** крок міграцій завершується успішно без змін у схемі

#### Scenario: БД недоступна під час деплою
- **WHEN** під час деплою на Vercel не вдається підключитися до БД (наприклад, Supabase-проєкт призупинено) або міграція завершується помилкою
- **THEN** деплой завершується помилкою з повідомленням, яке пояснює причину без розкриття секретів, а попередня успішна версія інстансу залишається активною

### Requirement: Безпечне паралельне застосування міграцій
Застосування міграцій SHALL бути ідемпотентним і серіалізованим. Якщо одночасно йде кілька деплоїв на ту саму БД, кожна міграція MUST застосовуватися рівно один раз.

#### Scenario: Два деплої одночасно
- **WHEN** два деплої (наприклад, production і preview) одночасно запускають міграції на тій самій БД
- **THEN** один чекає, доки інший завершить, і жодна міграція не застосовується двічі

### Requirement: Локальний білд без БД
Поза середовищем Vercel білд SHALL успішно завершуватися без змінних підключення до БД: крок міграцій пропускається з явним попередженням. У середовищі Vercel відсутність змінної підключення до БД MUST призводити до помилки деплою.

#### Scenario: Локальний білд без env
- **WHEN** розробник запускає білд локально без змінних підключення до БД
- **THEN** білд завершується успішно, а в лозі є попередження, що міграції пропущено

#### Scenario: Vercel-білд без підключеної БД
- **WHEN** білд запускається на Vercel без змінної підключення до БД
- **THEN** білд завершується помилкою з підказкою підключити Supabase через Vercel Marketplace

### Requirement: Базова схема закрита за замовчуванням
Базова схема БД SHALL містити лише службові дані каркаса. Ролі `anon` і `authenticated` MUST NOT мати прямого доступу до таблиць схеми `public`, ні до наявних, ні до створених пізніше міграціями. Доступ до даних іде лише через серверний код.

#### Scenario: Запит з anon-ключем
- **WHEN** клієнт звертається до будь-якої таблиці схеми `public` через Supabase API з anon-ключем
- **THEN** запит відхиляється або повертає порожній результат, і жодні дані не розкриваються

#### Scenario: Нова таблиця з наступної міграції
- **WHEN** пізніша міграція створює нову таблицю в схемі `public` без явних грантів
- **THEN** ролі `anon` і `authenticated` не мають до неї доступу

### Requirement: Позначка встановлення інстансу
Міграції SHALL створювати й ініціалізувати службовий запис інстансу з часом встановлення. Запис дає змогу відрізнити БД, яка доступна, але не ініціалізована, від ініціалізованої.

#### Scenario: Ініціалізована БД
- **WHEN** міграції застосовано
- **THEN** у БД є рівно один службовий запис інстансу з часом встановлення, і повторні деплої його не змінюють
