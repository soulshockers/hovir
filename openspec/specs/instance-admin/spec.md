# instance-admin Specification

## Purpose

Повноваження власника інстансу через `INSTANCE_PASSWORD`: захист створення презентацій паролем, попередження про відкритий інстанс і майстер-доступ `/admin` для списку, відновлення посилань і видалення.

## Requirements

### Requirement: Створення за паролем інстансу
Якщо `INSTANCE_PASSWORD` задано, створення презентації SHALL вимагати правильний пароль у тілі запиту. Пароль порівнюється у сталий час. Без пароля відповідь MUST бути 401 з кодом `password_required`, з неправильним — 401 з кодом `invalid_password`. Пароль MUST NOT передаватися в URL і потрапляти в логи.

#### Scenario: Правильний пароль
- **WHEN** `INSTANCE_PASSWORD` задано, і користувач створює презентацію з правильним паролем
- **THEN** презентацію створено

#### Scenario: Неправильний пароль
- **WHEN** користувач надсилає неправильний пароль
- **THEN** API повертає 401 з кодом `invalid_password`, і презентацію не створено

#### Scenario: Пароль не задано в інстансі
- **WHEN** `INSTANCE_PASSWORD` не задано
- **THEN** будь-хто створює презентацію без пароля, а поле пароля в UI не показується

### Requirement: Попередження про відкритий інстанс
Якщо `INSTANCE_PASSWORD` не задано, головна сторінка SHALL показувати помітне попередження, що будь-хто з адресою інстансу може створювати презентації, з поясненням, як задати змінну у Vercel. Якщо пароль задано, попередження MUST NOT показуватися.

#### Scenario: Відкритий інстанс
- **WHEN** користувач відкриває головну інстансу без `INSTANCE_PASSWORD`
- **THEN** сторінка показує попередження про відкритий інстанс

#### Scenario: Захищений інстанс
- **WHEN** користувач відкриває головну інстансу з `INSTANCE_PASSWORD`
- **THEN** попередження немає, а форма створення має поле пароля

### Requirement: Вхід у майстер-доступ
Маршрут `/admin` SHALL пропускати лише після входу з `INSTANCE_PASSWORD`. Успішний вхід видає HttpOnly-cookie сесії з обмеженим строком дії (12 годин), `SameSite=Strict` і `Secure` на HTTPS. Сесія MUST перестати діяти, коли змінюється `INSTANCE_PASSWORD`. Вихід видаляє cookie.

#### Scenario: Успішний вхід
- **WHEN** власник вводить правильний пароль на `/admin`
- **THEN** він бачить панель майстер-доступу, а наступні запити до `/admin` не просять пароль, доки не мине 12 годин

#### Scenario: Зміна пароля
- **WHEN** після входу власник змінив `INSTANCE_PASSWORD` і перезапустив деплой
- **THEN** чинна сесія більше не діє, і `/admin` знову просить пароль

#### Scenario: Запит без сесії
- **WHEN** запит до будь-якого API майстер-доступу надходить без чинної сесії
- **THEN** API повертає 401 без даних презентацій

### Requirement: Майстер-доступ вимкнено без пароля
Якщо `INSTANCE_PASSWORD` не задано, `/admin` SHALL показувати повідомлення, що майстер-доступ вимкнено, і як його увімкнути. API майстер-доступу MUST повертати 404.

#### Scenario: Інстанс без пароля
- **WHEN** користувач відкриває `/admin`, а `INSTANCE_PASSWORD` не задано
- **THEN** сторінка повідомляє, що майстер-доступ вимкнено, і не пропонує форму входу

### Requirement: Список усіх презентацій
Панель `/admin` SHALL показувати всі презентації інстансу: назва, дата створення, дата оновлення. Найновіші йдуть першими, по 50 на сторінку з навігацією. Список MUST NOT містити токенів чи їхніх хешів.

#### Scenario: Перегляд списку
- **WHEN** власник відкриває панель, а в інстансі 120 презентацій
- **THEN** перша сторінка показує 50 найновіших, і можна перейти до наступних

### Requirement: Відновлення посилань власником
Власник SHALL мати змогу відновити посилання будь-якої презентації. Оскільки в БД зберігаються лише хеші, відновлення атомарно перевипускає і edit-, і present-токен. Нові посилання показуються один раз з кнопками копіювання й завантаження `.txt`. UI MUST попередити перед дією, що попередні посилання автора перестануть діяти.

#### Scenario: Відновлення
- **WHEN** власник відновлює посилання презентації
- **THEN** він отримує нові edit- і present-посилання, а старі повертають 404

#### Scenario: Попередження перед відновленням
- **WHEN** власник натискає «Відновити посилання»
- **THEN** UI спершу пояснює, що чинні посилання автора перестануть діяти, і чекає підтвердження

### Requirement: Видалення презентації
Власник SHALL мати змогу видалити презентацію після явного підтвердження в UI. Видалення остаточне: після нього edit- і present-посилання презентації повертають 404, а її слайди й зображення у Storage видалено. Якщо зображення не вдалося видалити, презентацію MUST NOT бути видалено, а API повертає 503, щоб власник міг повторити дію. Видаляти презентацію MUST лише власник інстансу; edit- і present-посилання цього не дають.

#### Scenario: Видалення
- **WHEN** власник підтверджує видалення презентації
- **THEN** презентація зникає зі списку, її посилання повертають 404, а її слайди й зображення видалено

#### Scenario: Видалення неіснуючої
- **WHEN** запит видаляє вже видалену презентацію
- **THEN** API повертає 404

#### Scenario: Storage недоступний
- **WHEN** власник видаляє презентацію, а Storage не відповідає
- **THEN** API повертає 503, і презентація лишається в списку

### Requirement: Захист від міжсайтових запитів
API майстер-доступу, що змінюють стан, SHALL приймати запит лише з чинною сесією і заголовком `Origin`, що збігається з адресою інстансу. Запити з чужим чи відсутнім `Origin` MUST відхилятися з кодом 403.

#### Scenario: Запит з іншого сайту
- **WHEN** сторонній сайт надсилає запит на видалення з cookie сесії власника
- **THEN** API відхиляє запит з кодом 403, і презентацію не видалено
